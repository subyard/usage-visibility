Harnesses: local records and optional collection

Slide 3 compares Codex, Claude Code and OpenCode. Its rows are our collection categories, not a shared vendor hierarchy: traces are telemetry, alongside metrics and events. Inclusion of OpenCode restores the comparison; D13's implementation priorities remain unchanged pending clarification. Sources checked October 14, 2026; no user configuration or private session files were inspected.

Codex: local history, saved thread items and usage events, and telemetry. The repository's existing scripts/collect_evidence.py reads rollout timestamps, tool calls/results and token usage; this is a version-dependent local format, not a stable export API. Exporter settings separate logs, metrics and traces. Token categories include input, cached input, output and reasoning output; cached and reasoning counts are subsets, not extra tokens. User-prompt log content is opt-in. Log and trace exporters default to none; OTel settings belong in user-level configuration (project-local OTel settings are ignored). OpenAI usage/health analytics are separate from custom log/trace export; metrics default to Statsig, and analytics.enabled=false also disables custom OTLP metrics in the CLI.

Claude Code: local application data documents JSONL transcripts, prompt history and aggregate token/cost statistics. The transcript schema is internal; CLI session and subagent transcript cleanup defaults to 30 days. Aggregate statistics have a separate lifecycle. Native beta spans require CLAUDE_CODE_ENABLE_TELEMETRY=1, CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 and trace exporter configuration. API/tool spans carry elapsed timings; token categories include input, output, cache read and cache creation. Prompt/tool content export has separate opt-in controls (OTEL_LOG_USER_PROMPTS, OTEL_LOG_TOOL_DETAILS and OTEL_LOG_TOOL_CONTENT), which do not redact local transcripts. Tool-span duration includes permission waiting and execution, not CPU time. Provider operational telemetry is separate from export to our collector.

OpenCode: the storage documentation identifies local session/message data under ~/.local/share/opencode/ on Linux/macOS. The CLI exports a session as JSON; opencode stats summarizes tokens and cost. The v1.19.0 CLI message schema records input/output, cache read/write, reasoning, cost, tool input/output and timing fields. Usage availability depends on the provider; recorded cost is not proof of billed spend.

Native export is confirmed in release v1.19.0, pinned to 733b2c627e5aec39cb33cc22373bdce33053ef2c. The CLI runtime loads the observability layer. Its OTLP implementation sends logs to /v1/logs and traces to /v1/traces over HTTP when OTEL_EXPORTER_OTLP_ENDPOINT is set; without an endpoint these exporters are disabled. Optional headers use OTEL_EXPORTER_OTLP_HEADERS. No metric exporter is configured in this layer; this is a bounded source finding, not a claim about every version or plugin.

The published configuration schema and release CLI configuration include experimental.openTelemetry. The v1.19.0 CLI LLM path passes it to AI SDK telemetry, attaches session metadata and uses the configured tracer. The flag controls AI SDK call spans; it is not the switch for all runtime logs/traces. Coverage of other execution paths, subagent parentage and successful collector delivery still require a real-run check. The previous review inspected development config/runner files and missed the released CLI and shared exporter; its “native trace export: unverified” conclusion was incomplete.

Ready-made integrations also exist: MLflow's @mlflow/opencode documents conversation/tool traces, timing and tokens, exported after a turn when the session becomes idle. Langfuse's observability plugin documents turns, generations, tool calls, retries, reasoning and compaction. Its version 0.5.0 supports OpenCode 2 and OpenCode 1.18.29+; configuration uses plugins for v2 and plugin for v1. The community opencode-otel-plugin documents OTLP/HTTP metrics and traces. These are documented integrations, not locally tested deployments; compatibility and span semantics need validation before adoption. A custom adapter is therefore an option, not a prerequisite for all live collection.

The process-resource gap is our assessment of the documented telemetry catalogs: tool wall-clock duration does not measure child-process CPU or RAM. OS/process instrumentation and cross-harness task/agent/step correlation still require implementation and real-run validation. Existing candidate ratings are unchanged.
