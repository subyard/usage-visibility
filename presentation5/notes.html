My operating scale

Key idea

Different scales of automation bring different operational problems. This talk comes from using agents continuously in real development.

On the slide

My current scale: effectively using 1–2 billion tokens per day (98% cached input), about four nonstop sessions, roughly half running longer than a day. A publication-safe raster of the token table from presentation 3 provides a dated example, with daily totals and models retained and the financial column omitted. A short flow shows a human defining the task and checking the result at acceptance.

What I say

I work in software development. My current operating level is about four sessions running nonstop, using one to two billion tokens a day, with 98% cached input. Roughly half of these sessions run longer than a day. At this scale, the interesting problems include the environment, resource use and the work I have to do around the agents.

I am personally in the loop at least twice for each task: when I formulate it, and when I check and accept the work. I can talk to the agent more often when necessary. This is not continuous human supervision of every step, and it is not unattended acceptance of whatever the agent produces.

The screenshot is an earlier eight-day sample: 13.4 billion tokens, or 1.67 billion a day, with about five to seven sessions at that time. It supports the order of magnitude. My statement that I use this capacity effectively is my assessment of my own work; the token count alone cannot establish effectiveness.

Slide 02 ↗ · 1:30

The home directory problem

Key idea

Agents are not hostile. Post-training teaches them to solve the task, not to consider long-term consequences.

On the slide

The original Subyard opening composition: the large home-directory deletion headline on the left, the original terminal screenshot on the right, and attribution linked to the Reddit post. The supporting text states the operating principle above.

What I say

Agents are not hostile. They have been taught in post-training to solve the task we give them. We should not assume that completing the immediate task also means weighing all of its long-term consequences. The environment needs to bound what the agent can reach.

The screenshot comes from a user who reported losing their home directory during repository cleanup. The command shown reaches beyond the repository. This is the author's report, not an independently verified incident or explanation of its cause.

The same principle applies to quieter mistakes. If an agent can read projects for two clients, reusing one client's solution may solve the other client's task well while crossing an unacceptable boundary. Scope files, credentials, mounts and network access to the work the agent is actually doing.

Slide 03 ↗ · 1:40

Container or VM?

Key idea

Choose a real execution boundary and understand what it exposes. Harness controls remain useful as another layer.

On the slide

A shared-kernel container and a separate guest-kernel VM, with practical starting points: a devcontainer on GNU/Linux, a Linux VM on Windows, or a remote host/VPS. Directly under Devcontainer are links to Anthropic's example configuration and OpenAI's reference base image.

What I say

I use the harness's built-in restrictions too. For example, I want the agent to ask before committing. In my setup, I have not reached the reliable isolation I want using the harness alone, so I put the working environment inside a container or a VM as well.

For a Linux development workload on GNU/Linux, a devcontainer is a convenient starting point. It shares the host kernel and can provide the toolchain with little extra machinery. Anthropic publishes a complete Claude Code devcontainer example. OpenAI publishes codex-universal as a reference base image that can be used to prepare an environment; it is not a complete devcontainer configuration. On Windows, I would start with a Linux VM, or use a remote Linux machine. A VPS is often much more convenient when someone already provides it.

This is a recommendation for this workflow, not a claim that Windows cannot run containers. Linux containers on Windows commonly run through a VM-backed layer. A separate guest kernel also does not remove the need to check shared folders, forwarded services and credentials. Both choices need deliberate configuration.

Transition: once the boundary is in place, make the inside useful.

Anthropic: official devcontainer example; OpenAI: official reference base image; OpenAI: base image documentation; OpenAI: Dev Containers guidance; Docker: containers and VMs; Docker security; Microsoft: container isolation; Anthropic: OS-enforced sandboxing. Harnesses can enforce real OS controls; do not imply every harness restriction is only a prompt.

Slide 04 ↗ · 1:30

Give agents the tools to finish

Key idea

The agent needs a complete path from editing code to reproducing and checking the result.

On the slide

Edit → build → test → reproduce on staging. Two concrete environment gaps: a missing jq executable and a firmware task without access to its test board.

What I say

If the agent repeatedly says that jq is missing and falls back to grep, install jq in the working environment. A clever workaround may get through one task, but the same missing prerequisite will cost time on the next task as well. A recurring problem is a reason to repair the environment.

The same applies to larger prerequisites: compilers, test runners, fixtures, staging access and the services needed to reproduce a case. For firmware work, the agent may need a board, flashing tools and a way to read test output. It should be able to perform the verification expected of a developer doing that task.

Give it the authorized route to those resources. Access to a test board does not require arbitrary control of every device on the host. The next question is how to supply expensive or scarce capabilities without keeping one of everything alive for every session.

Transition: a complete environment makes compute demand much more visible.

The jq and test-board examples come from the presenter. Reusable provisioning is supported by the Dev Container Features specification. No claimed productivity improvement was measured for these examples.

Slide 05 ↗ · 1:40

Compute becomes the bottleneck

Key idea

Continuous sessions multiply build, test, staging and storage costs, even when each individual check is reasonable.

On the slide

Two observations from my work: 32 GB RAM is comfortable for about three sessions on smaller projects, and a roughly 60k-line Rust project can accumulate over 100 GB of build caches and artifacts per agent. CPU, RAM, disk/I/O and time are separate budget dimensions.

What I say

Efficient CI still costs compute. If five sessions run checks throughout the day, the total demand can be substantial. Staging environments also consume resources while agents prepare, wait, investigate or simply forget to release them.

For the smaller Android, Subyard and web projects I work on, a 32 GB host is comfortable for around three sessions. That is my workload observation, not a general sizing rule. Four ongoing sessions do not mean four maximum-size builds and staging environments all fit on that host at once.

Disk is another limit. A Rust project of around sixty thousand lines can leave more than a hundred gigabytes of caches and artifacts for each agent. Multiple checkouts, compiler versions and build configurations add up. Reuse compatible caches within the same trust boundary, and define retention rather than relying on unlimited disk.

Transition: occasional heavy work should draw from shared capacity.

Both numeric observations are supplied by the presenter; machine specifications beyond RAM, workload traces and disk inventories were not supplied or independently measured. Docker resource constraints supports the distinction between limits and physical capacity; it does not validate these personal figures.

Slide 06 ↗ · 1:40

Put heavy resources behind a broker

Key idea

A broker supplies a defined environment and allocates expensive capacity only while the task needs it.

On the slide

An agent requests a resource; a broker admits a lease; a temporary VM, emulator or hardware setup runs the heavy step. Two benefits are prominent: a known baseline and time-bounded capacity. The broker card links to the resource lease contract.

What I say

I want the agent to request a known environment instead of gradually changing an indefinitely shared machine. For a disposable VM or emulator, the next allocation starts from a defined baseline. The current task can change its own environment; those changes should not silently become the next task's starting point.

The agent should acquire the resource for the part of the work that needs it, save the useful results to its workspace, and release the allocation. It can keep working on code or reviewing a result without keeping a large test machine alive.

A broker is the service responsible for allocation and lifecycle. It can check capacity, enforce the supported resource shape and decide whether a request should wait. This pattern can be implemented with existing VM, container and device-management tools; it does not require a distributed scheduler. Shared images and reusable caches can have a longer lifetime than the disposable allocation.

Transition: the normal release path is only half of the lifecycle.

Adapted from Subyard slide 6. Implementation evidence: test VM broker; Android broker; lease contract. Hardware reset requirements depend on the board and test setup; disposable disks alone do not reset physical hardware.

Slide 07 ↗ · 1:30

Cleanup must outlive the agent

Key idea

The broker remains responsible when the agent stops or crashes. Reuse depends on verified cleanup.

On the slide

A lease has an owner, resource, lifetime and state. The failure path is expire → fence/stop/clean → verify. Failed cleanup quarantines the slot. The Subyard resource broker label links directly to its lifecycle and fencing documentation.

What I say

An agent can be interrupted, its session can disappear, or a wrapper can crash before release. Asking the agent to remember cleanup cannot cover all of those cases. The owner of the pool has to track each allocation independently.

A lease has a deadline and a way to stay alive while legitimate work continues. When it expires, the right to use that allocation ends. That is not proof that the old process has already stopped. The broker must revoke access, stop the workload and clean the temporary state.

Only after cleanup succeeds should the resource be issued again. If the broker cannot establish that a slot is clean, it should keep that slot unavailable for investigation. This also prevents a stale agent from affecting a new task that happens to receive the same resource later. Resource expiry is a control event; actual reclamation is work that has to happen and be checked.

Transition: the agent now needs to know how to request these capabilities.

Adapted from Subyard slide 7; Subyard resource broker: lifecycle and fencing; Subyard lease contract; Kubernetes Leases; Kubernetes cleanup controller. These Kubernetes mechanisms illustrate coordination and controller cleanup separately; a Lease object does not automatically clean arbitrary resources.

Slide 08 ↗ · 1:40

Agents should know their environment

Key idea

Make capabilities and instructions discoverable in the environment where the agent works.

On the slide

Organization supplies shared policies. User (container) supplies user-level AGENTS.md and skills; repository guidance supplies project AGENTS.md and skills. No filesystem paths are shown. The right-hand panel adapts the original Subyard discoverable-skills panel to a current Android example. Both the skill and the broker are clickable.

What I say

By self-aware here, I mean aware of the working environment: what tools are available, which resource it can request and what instructions apply. I do not want the agent to guess an API or invent another way to run an emulator.

There are organization-wide policies, user-level guidance and repository-specific instructions. The user level here means the user account inside the container. Its AGENTS.md supplies common working preferences, while user skills expose detailed procedures. The repository adds project-specific instructions and skills. The exact file discovery and precedence rules depend on the harness; this is a model for ownership of guidance, not a universal AGENTS.md search algorithm.

In Subyard, provisioning the Android profile installs a real skill called subyard-android. It explains how to inspect the emulator catalog and pool status, then run a command with a broker-managed lease. The wrapper handles renewal and release. The skill tells the agent how to use a capability; the broker still decides whether it is ready and available. Merely finding a skill is not permission to use everything behind it.

Transition: making instructions available does not mean loading every instruction into every task.

Slide 09 ↗ · 1:25

Keep instructions small and useful

Key idea

Instructions, documentation and generated code require active pruning. Keep the information that improves decisions.

On the slide

Illustrative accumulated instructions give way to useful constraints and procedures loaded as needed. The maintenance loop is review → prune → recheck.

What I say

Agents are very chatty. In commercial projects I repeatedly remove unnecessary explanation, duplicated documentation and code that does more than the task needs. In my experience they do not reliably judge which text will still matter to the next person.

The same maintenance applies to my own instructions. Agents can infer many ordinary steps. A rule I added to fix one failure can later cause extra work, unnecessary reports or repeated checks. After tools or models change, I sometimes discover that an old instruction is now the bottleneck.

I keep rules that describe real constraints or prevent a recurring mistake. I put longer procedures in skills so they can be loaded when relevant. Minimal does not mean deleting necessary detail. It means keeping enough useful information for the work, then checking that the rules still have the intended effect.

Transition: to decide what to remove or change, we need evidence from actual work.

Personal observations from the presenter; Anthropic: effective context engineering supports sufficient, high-signal context and progressive loading. This source does not establish that the shortest instruction always performs best, or that any fixed number of tokens is optimal.

Slide 10 ↗ · 1:40

Observability across a team

Key idea

Collect correlated evidence about tokens, compute, time and outcomes, preferably across the team working on one codebase.

On the slide

A flow from people and agents through correlated observations to improvement decisions. Three questions cover tokens, compute and time. The Usage Visibility link opens the existing PDF on GitHub.

What I say

The first priority is collecting the data. A dashboard cannot reconstruct what was never recorded. I want to connect the task, agent and step to model usage, processes and temporary resources, including a staging lease.

It is more useful to do this at the scale of the team sharing a codebase. Then we can see repeated build problems, missing prerequisites and long waits across several developers and agents. A fix to the environment or test workflow can benefit everyone working there.

Token totals alone are insufficient. A cheap model can repeatedly trigger an expensive test suite. A long tool call may be waiting rather than using CPU. We should distinguish actual CPU and memory use from reserved capacity and how long a resource is held. Missing instrumentation should remain visible as a gap, not become a fabricated zero.

Transition: once the evidence exists, the agent itself can help review it.

Slide 11 ↗ · 1:40

Ask the agent how to improve

Key idea

An agent can identify promising workflow changes from recent work, but its report still needs validation.

On the slide

An anonymized native HTML prompt asks the agent to review its workflow. Four generic recommendations cover less coordination chatter, selective reruns, early prerequisite checks and releasing resources when finished.

What I say

I can ask the worker agent to review recent work: where did we spend tokens unnecessarily, and were temporary resources held longer than needed? This publication-safe example summarizes the method without exposing session records or internal incident details.

These recommendations are practical hypotheses. I can inspect a repeated test run and decide whether anything changed between the runs. I can check that prerequisites are ready before allocating expensive resources. I can verify that a resource was released when its work finished.

Some waiting and coordination is necessary. A review does not establish an exact amount of waste or wasted resource-hours. Use the report to choose an investigation, validate the cause, change the workflow and observe the result.

Slide 14 ↗ · 1:15

You are responsible

Key idea

LLMs have uneven capabilities. Design their access deliberately and verify the work you accept.

On the slide

A direct closing statement: LLMs are not people; they can be smart in some areas and badly wrong in others.

What I say

LLMs are not people. They can solve something that looks difficult and then make a very poor decision in a situation that looks obvious to us. A strong answer in one area is not evidence that the next decision will be sound.

Think twice about what the agent can see and change. Check where the effective boundary is in your setup: mounted files, credentials, network access and the authority to allocate or destroy resources. Make that match the task you intended to delegate.

I remain responsible for the task definition and the result I accept. That brings us back to the first slide: I talk to the agent when I give it the work, and I personally inspect the work at acceptance. Good tools and a well-designed environment make those checkpoints more effective.

Transition: leave the presentation link visible for questions.
